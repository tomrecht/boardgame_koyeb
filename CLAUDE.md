# Board Game GNN — TD(λ) Training Project

Context for Claude Code picking up this project. Owner (Tom) prefers: terse
responses, minimal surgical edits with unambiguous paste locations, full
function rewrites over partial diffs for substantial changes, no rewriting
of working code unnecessarily.

## Project background

Custom hub-and-spoke dice board game. Full stack built from scratch: game
engine (`game.py`), Flask backend (`app.py`), Phaser.js frontend (`game.js`).
Current AI approach: GNN value network (`network.py`) driving 2-ply move
selection (`agent_gnn.py`), trained via self-play. Strongest checkpoint to
date: `best_iter5_m46.pt`.

An earlier heuristic evolutionary track (`train.py`) reached 90%+ vs.
baseline but was recognized as fundamentally limited without a neural
approach and is no longer the active line of work.

## Current phase: TD(λ) fine-tuning

Supervised fine-tuning on top of self-play was tried and ruled out — it
decoupled from actual move quality (val accuracy improved while playing
strength did not), hitting a parity ceiling. TD(λ) replaces the
Monte-Carlo target (final game outcome stamped on every position) with a
bootstrapped λ-return, intended to give better credit assignment without
that decoupling.

Two modes, both implemented and validated:

- **Mode B** (`train_td.py`, CLI) — offline sanity check on existing
  recorded positions (off-policy data — heuristic/earlier self-play, not
  generated by the current model). Confirms the TD *mechanism* works
  (target computation, target-net refresh, training loop). Does **not**
  predict on-policy strength gain — the off-policy/on-policy gap means a
  good loss curve here doesn't transfer to a strength claim.
- **Mode A** (`td_selfplay_loop.py`'s `run_td_selfplay`, driven by the
  standalone script `run_full_td.py` — plain `.py`, not a notebook; no
  `.ipynb` exists in this repo) — the real training loop. Iterative
  on-policy self-play → λ-return targets → train → gated evaluation →
  promote/checkpoint. This is the one that can actually move strength and
  is expected to answer whether TD resolves known behavioral rough edges
  (see "Open questions" below).

## Design decisions and reasoning

- **`lam=0.9`, `gamma=1.0`** — λ=1 reduces exactly to the Monte-Carlo target
  (what self-play/supervised already used); λ=0.9 is a conservative first
  step toward bootstrapping, not a jump to something aggressive. γ=1.0
  (no discounting) because this is a finite, turn-limited game — no
  infinite-horizon shaping needed.
- **Target net refreshed every epoch** (not every batch, not once per
  iteration) — standard fix for bootstrapping off a still-updating live
  model, which causes targets to chase the weights and training to
  oscillate. Per-epoch refresh is deliberately the middle ground.
- **`uniform_weights=True`**, NOT the older `1/ply_from_end` down-weighting.
  That scheme existed to compensate for MC targets being noisier further
  from the game's end. TD's bootstrapping already reduces that variance at
  the source — reapplying the old weighting would double-discount exactly
  the early/midgame positions TD is meant to improve.
- **`lr=1e-4`** (dropped from the initially-carried-over `2e-4` for the real
  Mode A run) — the smoke test's iter1 fell to 30% win rate vs. the champion
  after just one update, consistent with steps too large for fine-tuning a
  model that's already near-parity from a strong warm start. Halving lr
  directly targets that failure mode. `batch_size=32` unchanged — no
  evidence yet that it needs to differ from what worked for supervised/
  self-play training on this architecture.
- **`games_per_iter=300`** (cut from the original `800`) — on-policy
  generation (`use_heuristic_opp=False`) is the actual design principle
  here (TD bootstrap targets only mean something if the data reflects the
  policy being evaluated), not the number 800 itself. At this hardware's
  measured self-play throughput, 800 games/iteration would cost roughly
  40 minutes of generation alone per iteration; 300 trades some
  per-iteration data volume for wall-clock, recovered via the replay
  buffer below.
- **Replay buffer (`replay_iters=3`)** — each training update pools the
  current iteration's games with the previous 2 iterations' (already in
  memory, zero extra generation cost), recovering most of the data volume
  lost by cutting `games_per_iter`. Trade-off: training data is up to 2
  iterations stale (mildly off-policy), but far less stale than Mode B's
  data, and standard practice in this style of loop. `game_id`s are unique
  across iterations (derived from the never-overlapping generation seed
  blocks), so `split_by_game` groups pooled records correctly.
- **`seed_base=10_000`, incrementing per iteration** — guarantees no seed
  collisions within one Mode A run (self-play generation is entirely
  in-memory per iteration; no `.jsonl` file is ever read during Mode A).
- **Paired-seed evaluation**: eval game pairs `(2k, 2k+1)` (color-swapped,
  challenger plays both colors) share one dice-stream seed instead of each
  game getting an independent seed — cancels dice-luck variance across the
  pair, giving a sharper win-rate signal from the same `eval_games` budget.
- **Seed-overlap watch-out**: generation and eval seeds must stay in
  disjoint ranges, and this is *not* automatic — generation uses
  `seed_base + it*games_per_iter + i`, so shrinking `games_per_iter` shrinks
  that block and can silently let a fixed eval-seed formula collide with it.
  Hit this directly: dropping `games_per_iter` 800→300 without moving the
  eval offset caused eval and generation to share seeds. Fixed by giving eval
  its own high, disjoint block: `seed_base + 1_000_000 + it*eval_games`.
  Any future change to `games_per_iter`, `eval_games`, or `seed_base` should
  re-verify the two ranges (and eval-vs-eval across iterations) stay disjoint
  for the full planned iteration count — don't assume it, check it (e.g. by
  computing the seed sets in Python and asserting the intersection is empty).
- **Promotion gate: `eval_games=200` paired-color games vs. the current
  CHAMPION (not vs. the model's own previous iteration), `promote_winrate
  =0.55`** (not bare 50%) — deliberate margin above parity to guard against
  200-game sample noise and against slow drift via repeated marginal
  "wins." Every iteration checkpoints regardless of promotion; only the
  champion snapshot updates on promotion. This ratchet design is carried
  over from what already worked to produce iter5.
- **SPRT futility early-stop on eval** — after each decisive eval game, a
  Sequential Probability Ratio Test (H0: true win rate ≤0.50, H1: ≥0.60,
  bracketing the 0.55 gate; `alpha=beta=0.02`) can abort the remaining eval
  games once continuing is statistically futile. Only the *lower* (futility)
  boundary is ever acted on — a run trending toward promotion always plays
  out the full `eval_games`, so `promote_winrate`'s noise-robustness is
  unchanged for any actual promotion decision; this only cuts time on
  iterations that are clearly not going to promote. Validated by direct
  simulation before use — see Learnings for the numbers, including the one
  real caveat (elevated false-stop rate for a model sitting exactly at the
  0.55 gate, inherent to any two-hypothesis SPRT's indifference zone).
- **Eval dispatch is batched**, not all `eval_games` submitted to the pool
  at once — `Pool.imap_unordered` queues its entire task list up front
  regardless of how fast the consumer reads results, so without batching an
  SPRT-triggered early stop would still leave workers grinding through the
  full remaining set in the background, silently forfeiting the time
  savings it's meant to provide.
- **Device discipline**: GPU/accelerator used only in the main process
  (target model + encoding); `network.py`'s `DEVICE` now has an MPS branch
  (`cuda` → `mps` → `cpu`), added and empirically confirmed working on the
  M3 Pro (trains without NaN/divergence, loss magnitudes comparable to Mode
  B). Self-play workers are still forced CPU-only — note `CUDA_VISIBLE_
  DEVICES=""` alone doesn't gate MPS (no MPS equivalent of that env var);
  what actually keeps workers off the GPU is `_pool_worker_init`'s explicit
  `_net.DEVICE = torch.device('cpu')` override after import. `mp.get_context
  ('spawn')` used deliberately — fork/forkserver caused CUDA-context
  deadlocks previously.
- **`n_workers=8` tuned empirically, not assumed from core count.** M3 Pro
  is 11 cores (5 performance + 6 efficiency). The "match performance-core
  count" heuristic (→5) undersold this chip: a direct generation-throughput
  benchmark (`bench_workers.py`) showed 8 workers much faster than 5.
  Swept 9-11 as well — no significant further gain over 8, so 8 is the
  settled value (diminishing returns past that point, as expected once
  the main process/OS start losing headroom). Re-benchmark if the hardware
  or workload shape changes materially.
- **Progress reporting**: `tqdm` bars never rendered visibly in this setup
  (likely stderr output getting lost amid multiple worker subprocesses
  writing to the same terminal) even though the underlying loop worked
  correctly. Removed entirely from `game_worker.py`; both
  `generate_games_parallel` and `evaluate_parallel` now print a plain status
  line every ~10% of games instead — simpler and actually visible in a
  plain-terminal, multi-process setting like this one.
- **Always launch the run with `python -u`** (unbuffered). Piping stdout to
  `tee` makes Python switch from line- to block-buffered output, so
  `print()` progress sits invisibly in a buffer until it fills or the
  process exits — this looked exactly like a 15-minute hang at "Starting 8
  workers" on the first real launch when the workers were in fact already
  generating games. The correct command is
  `caffeinate -i python -u run_full_td.py 2>&1 | tee -a td_run.log`.
- **Workers disable autograd process-wide** (`torch.set_grad_enabled(False)`
  in `_pool_worker_init`). Workers only ever run inference. The model's own
  forward passes in `agent_gnn.py` are already under `torch.no_grad()`, but
  the per-move board **encoding** (`encoder.encode`, called once per
  candidate move) runs *outside* those blocks and was paying the
  VariableType autograd-dispatch tax on all its gather/scatter/view ops —
  visible as `torch::autograd::as_view` / `VariableType::select_int` /
  `scatter_gather` dominating a `sample` profile of a worker. Disabling grad
  globally in the worker is safe (no training there) and removes that
  overhead from every op, encoding included.
- **Debugging a "stuck" worker on macOS**: `py-spy dump` needs the terminal
  granted Developer Tools access (Privacy & Security) — `sudo` alone hits
  "Operation not permitted." The Apple-signed built-in `sample <pid> <secs>`
  works without that and gave the profile that identified the autograd
  overhead above. General rule already seen twice: workers pegged at ~100%
  CPU means compute-bound (slow / real work), not deadlocked — profile
  before assuming a hang.

## Learnings so far

- Mode B ran clean end-to-end: val loss plateaued around **0.036** across
  12 epochs (early-stopped), sign-accuracy around **0.67**. Read as a
  structural pass (mechanism works, stable, no NaN/divergence) — not a
  strength signal, per the off-policy caveat above. Flat-from-epoch-1
  plateau is plausible/expected given warm-starting from an already
  self-play-trained model on data whose targets are close to MC (λ=0.9).
- Iterating further on Mode B hyperparameters has limited value: findings
  don't reliably transfer to Mode A's on-policy setting, and compute is
  better spent on an actual Mode A run.
- **Smoke test** (2 iterations, `games_per_iter=50`, `eval_games=50`, on
  MPS): ran clean end-to-end — pool start, MPS training, eval all worked,
  no crashes/NaN. Gave a real per-iteration wall-clock number: ~1600-1700s
  at that (much smaller) scale, dominated by CPU-only self-play generation
  and eval (~13-15s/game with 5 workers) rather than training (a few
  minutes on MPS).
- Both smoke iterations showed val loss bottoming early (epoch 3, then
  epoch 6) then climbing while train loss stayed flat/noisy — expected
  small-sample overfitting at only 50 games/iteration, not a bug:
  `train_on_records` already keeps the best-val epoch's weights, not the
  final epoch's. Expected to look different (closer to Mode B's plateau)
  at real scale, and further mitigated by the replay buffer added
  afterward.
- Win rate vs. champion swung 30%→50% across the two smoke iterations —
  read as pure noise at only 50 eval games, not a signal on
  hyperparameters; the real run's `eval_games=200` is far larger.
- **SPRT futility bound validated by direct simulation** before adopting
  it: a 30%-true-win-rate model (matching smoke iter1) triggers a futility
  stop around game 23/200 (~88% eval-time cut for that iteration);
  false-stop rate is ~1% at a true win rate of 60% (matches the
  `alpha=beta=0.02` design target) but rises to **~16%** for a model
  sitting exactly at the 0.55 gate itself — inherent to any two-hypothesis
  SPRT's indifference zone, not a flaw in the implementation, and not a big
  departure from that edge case's already-coin-flip character under the
  original full-200-game design.
- **Game-logic optimization (branch `optimize-game-logic`) proven safe by
  deterministic A/B**: `shortest_route_to_goal`/`all_goal_distances` BFS
  blocking checks replaced with `neighbor.index not in blocked_key`
  (equivalent *by definition* — `_get_blocked_key` returns exactly the
  frozenset of blocked tile indices), plus the numbered-piece
  `all_goal_distances` result dict is now cached like the unnumbered path's
  already was. Verified by playing 6 identical-seed games on old vs. new
  code with `PYTHONHASHSEED=0` and byte-diffing full trajectory dumps:
  **byte-identical**, and 7.7% faster in a paired same-load timing. Method
  note for future perf work: this trace-diff (scratchpad copies of the repo,
  pinned hash seed, dump per-position records minus the wall-clock game_id)
  is the standard of proof to use — single-run "it didn't crash" tests and
  cross-process profile comparisons both proved misleading here.
- **Self-play is not run-to-run deterministic by default**: candidate move
  pairs reaching transposed-identical positions get identical GNN scores,
  and the argmax tie-break follows `set` iteration order, which depends on
  Python's per-process string hash seed (move tuples contain strings). Same
  seeds therefore produce different games across processes unless
  `PYTHONHASHSEED` is pinned. Harmless for training (dice seeds still
  control the real randomness) but essential to know for any exact
  reproducibility or A/B comparison.
- **Profiling learnings**: cProfile on a directly-called `worker_play` (see
  `profile_worker.py`) attributes Python-level time reliably; macOS `sample`
  only shows C frames, and `py-spy` fought macOS permissions repeatedly.
  Profile before optimizing: the GNN forward was NOT the generation
  bottleneck — Python BFS/path code was ~35% of worker time; and beware
  benchmarking against a live training run's shifting background load
  (torch kernel timings "improved 28%" purely from load variance).
- **Found and fixed a real seed-collision bug** from combining two changes:
  cutting `games_per_iter` 800→300 caused the (unadjusted) eval seed formula
  to collide with generation's seed block. See "Seed-overlap watch-out"
  above — fixed, but a reminder that these two ranges need re-verification
  whenever related parameters change.

## Current benchmark

`best_iter5_m46.pt` is near human strength but still short of parity
against its strongest tester (Tom), who beats it ~55-60% of the time. The
TD champion one iteration on (`td_champion`, = promoted iter1) plays
similarly: 9/16 for Tom (~56%), i.e. no measurable strength change yet at
one iteration removed. Known rough edges observed in play
(may or may not be resolved by TD — open question, not yet root-caused
as a code defect): occasional pass-over-save-looking decisions, and
occasional offgoaling of a numbered piece in the endgame. Plan is to run
TD first and see if better value estimates resolve these before doing any
separate hand-debugging.

Goal-pair blocking bias (exploration gap, NOT expected to be fixed by TD).
Owner (Tom) clarified the domain reasoning: blocking certain goal *pairs*
can be an *absolute* block — a structural dead-end where the opponent has
**zero** path to either goal, not merely a slowed one — which makes it a
genuinely strong, high-value strategy. Three pairs afford this: 2&4, 1&6,
3&5 — and owner confirms all three are **equally easy to block** (true board
symmetry), so any preference among them is a pure exploration/coverage
artifact, not board geometry. `best_iter5` strongly and consistently favors
**2&4** (goes for it almost every game); the current TD champ (promoted
iter1) inherited the same bias. This is an *exploration* deficiency —
self-play found one instance of a strong pattern and under-explores its
symmetric variants — and the GNN is not generalizing the symmetry on its own
(or it would already value all three pairs equally).

Measured baseline (8 self-play games from `best_iter5`, detection below):
per-goal denial rate — goal 2 32.9%, goal 4 25.5% vs goals 1/3/5/6 all in the
~2-10% range. Robust conclusion: **2&4 is strongly preferred over the other
two pairs** (2&4-denial in 7/8 games). NOT robust at n=8: any finer ordering
among 1&6 vs 3&5 — which pair a given game sets up is high-variance,
strongly influenced by opening piece order, so the non-2&4 breakdown is noise
here. A trustworthy per-pair baseline needs ~hundreds of games (a pair block
is a game-level ~binary event); deferred until the exploration experiment is
actually built. **Detection is free** and needs no board geometry: goal g is
"denied" against a player iff that player's (non-saved) numbered piece g is at
INF_DIST (`shortest_route_to_goal == INF`, already computed as the encoder's
`is_completely_blocked`). Exclude saved pieces — a saved piece can read INF if
its path is sealed *after* it scored, but it already succeeded. This per-goal
signal (not pair-both-only) is the right diagnostic primitive.

Corollary from the opening-order sensitivity: **opening randomization** is
likely an especially high-leverage exploration lever for this gap — it
diversifies which pair the game steers toward at the source, potentially
surfacing 1&6/3&5 setups without any per-move noise. See EXPLORATION_SPEC.md.

Key implication: **TD(λ) is not expected to resolve this**, unlike the
offgoaling / pass-over-save edges. TD changes the training *target*
(bootstrapped λ-return); it improves credit assignment only for states the
greedy self-play policy actually visits. Since the net rarely values the
1&6/3&5 blocks it visits them rarely, so little outcome data about those
blocks is generated — and TD can only sharpen values for states that are
actually experienced, not drive the policy to experience new ones. TD adds
no exploration and no symmetry prior. The natural fixes are post-TD and exploration-side, not target-side:
(a) **symmetry augmentation** — transform recorded (position, target) pairs
under the goal-pair symmetry to synthesize experience with the other two
pairs directly (cheap/targeted, valid only if the transform is a true board
automorphism); (b) **self-play exploration noise** — temperature / root
noise / opening randomization so self-play occasionally tries the other
blocks and learns their value from real outcomes (AlphaZero-style coverage
fix, larger change to the loop). Still parked for now, but no longer
expected to self-resolve via the TD run.

## Next steps (in order)

1. Let the full Mode A run proceed — watch `td_run.log` / the terminal for
   per-iteration win rate and val loss trends to judge whether it's still
   trending up or has stalled.
2. On any crash/interrupt, just re-run the exact same launch command —
   `run_full_td.py` resumes automatically from the latest `td_iterN.pt`.
3. Once the run concludes (or is deliberately stopped), evaluate whether
   the known rough edges (pass-over-save-looking decisions, endgame
   offgoaling, and the parked 2-4 goal-pair bias) persist post-TD before
   considering any separate targeted debugging of them.
4. **Exploration as a separate, ceiling-raising lever (after TD, not
   during).** Self-play generation is currently *fully greedy* — move
   selection is 2-ply `argmax` over the value net (verified: no temperature,
   softmax, multinomial, epsilon, or root noise anywhere in `agent_gnn.py`
   /`td_selfplay_loop.py`); the ONLY stochasticity in generation is the dice
   seeds. Consequence: the policy never deliberately tries a move it
   currently undervalues, so any strong strategy the net doesn't already
   rate highly is never generated, never trained on, never discovered — a
   self-reinforcing coverage collapse (the 2&4-vs-1&6/3&5 goal-pair gap is
   the one *visible* instance because symmetry exposes it; others without a
   symmetric twin are invisible but produced by the same mechanism). This is
   orthogonal to TD: TD is credit assignment (learn the value of visited
   states efficiently), exploration is coverage (which states get visited at
   all). TD polishes inside the box greedy self-play has found; it cannot
   enlarge the box. So part of the standing ~55-60% gap to the human tester
   is plausibly *undiscovered strategy*, not *mis-valued known strategy*, and
   no amount of better credit assignment reaches that part. Candidate
   interventions (a new experiment, validated by end-to-end strength over a
   full run — NOT by byte-identical trace, since they deliberately change
   play; scoped to GENERATION only, eval must stay greedy): temperature/
   softmax move sampling in the opening, AlphaZero-style root Dirichlet
   noise, opening-position randomization (all annealed toward greedy later),
   and symmetry augmentation to harvest known board invariances for free.
   Deliberately NOT folded into the current run: doing so would confound the
   clean "what does TD alone do?" question — and iter3 is the very first
   iteration trained on the corrected (un-stale-blocked) features, so the
   clean TD signal hasn't even been observed once yet. Sequence: get a few
   corrected-feature TD iterations first, then run exploration as its own
   tuned experiment.
